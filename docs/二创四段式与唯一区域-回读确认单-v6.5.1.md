# 二创四段式与唯一区域 · 需求回读确认单（v6.5.1）

> 本单把用户原话翻成验收句，落盘留痕。大白话优先，物理边界如实写。

## 一、用户原话

> "然后你在云境里单独开了一个区域了吗，专门用来盛放所有玩家二创版本云境的板块，一定不能乱啊，全部的二创版本只能在这一个区域内，然后玩家每次上传二创版本的结构都是简介+特点+二创内容+打包源码"

## 二、翻译成验收句（逐条可验）

| # | 验收句（怎样算做对） |
|---|---|
| A1 | 云境内存在**唯一**二创入口（工具→二创版块），玩家所有的浏览/下载/发布都只在这一处完成，不散落到第二处。 |
| A2 | 所有二创作品在 GitHub 侧只落在**唯一标签** `二创投稿` 的 Issues；包体只落在**唯一目录** `community/packages/`；不存在第二个标签、第二个目录存放二创作品。 |
| A3 | 每件作品正文固定为**四段**且顺序一致：`简介` → `特点` → `二创内容` → `打包源码`；四段都有明确标记与标题，缺段视为不合规。 |
| A4 | 发布表单强制填齐这四段对应内容后才能提交；段内为空则拦截。 |
| A5 | 列表与详情按这四段渲染；玩家一眼能看到某作品的简介、特点、改了哪些内容、包体在哪。 |
| A6 | 新增一件作品后，GitHub 上该 Issue 的四段与包体目录同步就位，按时间倒序排在最前。 |
| A7 | 既有 v6.5.0 作品（只有单段 note）能被兼容读取，不至于打不开。 |

## 三、必须如实说明的物理边界（不假装支持）

1. **"打包源码"的真相**：网页**读不到**玩家电脑/手机磁盘上的云境源码文件（尤其手机）。因此"打包源码"这一段打包的是**内容层的二创源码**——即玩家在云境内改动过的 DLC / 世界书 / 预设 / 插件定义 / 正则 / 存档 / 资源等**明文数据**（`manifest.json` + `content/*.json`），这些就是"可以被玩家继续修改的源码"，不是云境主程序的 `.js` 文件本体。桌面 Chrome/Edge 手动授权项目目录后可附加真 `.js` 源码，但那是可选轨，不是默认能力。
2. **唯一区域 ≠ 单文件**：GitHub 一个 Issue 正文有字节上限，大包（图片/视频/大世界书）无法塞进正文，故正文放"打包源码"段的**索引信息 + 包体链接**，包体实体统一存 `community/packages/` 这一个目录——仍是"唯一目录"，不散落。
3. **token 现实**：本 token 无 Gist 写权限（实测），但有仓库 contents 与 Issues 写权限。故包体走仓库目录（比 Gist 更稳），上传由云境内发布流程自动完成，玩家只点确认。
4. **"开发者不参与内容"**：自动化只做"打包 + 上传 + 建索引"，不审核、不改动内容本身，符合用户此前定下的边界。
