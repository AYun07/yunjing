# 酒馆（SillyTavern）多 API / 智能体机制调研

> 调研背景：云境「副 AI 变量 / 副 AI 摘要」要走通多后端分流，遂考察酒馆这类纯前端卡（重前端、轻后端）如何处理「多个 API、多个模型、按角色分流」的问题，取其可借鉴的设计落到 `js/connection-profiles.js`。
>
> 调研时间：2026-11-01 ｜ 对应版本：v3.55.30

---

## 一、核心结论（先说人话）

> **多模型分流的本质，不是「炫技」，而是把机械活丢给廉价模型，让主叙事保住声线一致、还省 token。**

静态叙事 App 的瓶颈从来不是「连不上模型」，而是：
1. 主叙事每次都要从头带着全部状态上下文，贵且慢；
2. 变量登记、前情摘要这类「结构化机械活」和「文学生成」抢同一个上下文窗口；
3. 想换更便宜/更稳的模型跑机械活，又不想动主叙事的钥匙。

酒馆给出的范式是：**Connection Profiles（连接配置）+ 角色指派**，把「用哪个后端」从「写死在代码里」变成「用户可配、可一键切换、可按角色分配」。

## 二、酒馆现有的几套机制（考察到的）

| 机制 | 形态 | 解决什么 | 云境可借鉴点 |
| --- | --- | --- | --- |
| **Connection Profiles**（官方内置） | 存 API 类型 / URL / Key / 模型 / 模板，可在界面 `/profile` 切换 | 同一前端接多个后端（OpenAI / Claude / 本地 / 第三方代理），不改代码 | 把主叙事 / 副AI变量 / 副AI摘要 拆成独立 Profile |
| **ST-Multi-Model-Chat** | 群聊场景按「角色」分配不同 Profile | 一个房间里不同角色走不同模型 | 副 AI 角色天然就是「另一个模型」 |
| **api-config-manager** | 无限配置、一键切换 | 重度玩家要管理几十个 Key / 端点 | 配置增删改 + 角色指派的最小闭环 |
| **副 AI 做变量 / 摘要** | 副 AI 专职抽取状态、生成前情 | 机械活不占主叙事上下文 | 直接对应云境「状态登记官 / 前情提要官」 |

### 关键观察
- 酒馆的「Profile」是**纯配置对象**：没有隐藏的全局单例，切 Profile 就是换一个 config 喂给同一套调用逻辑。这点和云境此前 `storyVarApi` 单例写法（全局一个、改了影响所有人）形成鲜明对比。
- 「按角色分流」本质是**在调用点决定 cfg 来源**：主对话用主 Profile，副 AI 抽取用副 Profile——调用函数本身不变，变的只是 `resolve(role)` 返回的 config。
- 副 AI 跑廉价模型是被广泛采用的省钱写法：**变量登记 / 摘要是结构化输出，不需要顶级文笔**，用便宜快模型完全够，还能把主叙事的上下文留给真正的文学生成。

## 三、落到云境的设计

### 3.1 数据模型
```text
localStorage['yunjing.profiles']      = [ { id, name, type, endpoint, apiKey, model,
                                           maxTokens, temperature, timeout } ]
localStorage['yunjing.profileRoles']  = { varAI: <profileId|__legacy__|__main__|null>,
                                           summary: <profileId|__legacy__|__main__|null> }
```

### 3.2 三个角色
| 角色 key | 语义 | 原系统对应 |
| --- | --- | --- |
| `main`（主叙事） | 主线文学生成 | 沿用原 `storyVarApi` 主配置 |
| `varAI`（副AI变量·状态登记官） | 抽取/登记变量 | 原第三接口 |
| `summary`（副AI摘要·前情提要官） | 生成前情提要 | 新增角色 |

### 3.3 调用契约
- `ConnectionProfiles.resolve(role)`：**已指派且字段填全**才返回配置，否则 `null` —— 调用方据此走兜底（旧单配置 / 主配置）。
- `migrateLegacy()`：首次运行把旧 `storyVarApi` 单配置迁成默认连接并指派 `varAI`，用户无感升级（哨兵 `yunjing.profilesMigrated`）。
- `variable-ai.js::activeConfig()` 优先 `resolve("varAI")`，无则回退旧版单配置；`recapCall / recapReady` 增加 `summary` 解析路径。

### 3.4 为什么这样解耦
沿用酒馆「Profile 是纯配置对象」的思路：
- 切换后端 = 改一个 config，不动调用逻辑；
- 加新角色 = 加一个 role key + 一处 `resolve`，不碰主流程；
- 用户可把「变量登记」指向便宜模型、「主叙事」指向强模型，直接在 UI 里配，无需改代码。

## 四、顺带挖出的真实 bug（与本次调研同期修复）

调研时实测真实 LLM 的每轮请求数，发现此前用短 mock 测到的「每轮 2 次请求」是**假象**：

- 真因：`extractBody` 的章节标题剥离正则把以「**第N回合：叙事正文…**」起头的首段误判成假章节标题删空 → 正文长度归零 → 触发自动重写通道，多发一次请求。
- 修复：判别式收紧为「无句读的真标题」才剥；并补**契约校验熔断**（回复已结构合规就跳过自动重写）。
- 结果：真实 LLM **稳定 1 请求/轮**，7 轮零崩溃、堆 9–12MB。

> 这个 bug 反证了调研价值：把「多后端分流」想清楚后，顺手把请求数模型也理顺了——**契约合规就不该重写**，和酒馆「副 AI 只干机械活、主叙事一次成型」的思路一脉相承。

## 五、后续可拓展方向（备忘）
- 角色可扩展为 N 个（如「战斗解说官」「地图推演官」），只需 `profileRoles` 增加 key。
- 支持 Profile 级别的「失败自动降级到主配置」（参考酒馆的 key 轮换）。
- `resolve()` 可缓存解析结果，避免每轮重复读 localStorage。
